## Навіщо це QA

Ти вже знаєш техніку тест-дизайну **аналіз граничних значень** (boundary value analysis): баги живуть
на межах діапазонів. Ось звідки вони беруться в коді:

```js
function getCategory(statusCode) {
  if (statusCode > 200 && statusCode < 300) return 'success';
  return 'error';
}

getCategory(201); // 'success'
getCategory(200); // 'error' ← найпоширеніший статус HTTP — і це «помилка»
```

Розробник написав `>` замість `>=`. Один символ — і звіт про тести показує сотні «помилок» там,
де все добре. Коли ти сам пишеш умови в автотестах і утилітах, ти робиш ті самі помилки. Тому в цьому
уроці ми не лише вчимо `if`, а й тестуємо межі — так, як ти це робив руками.

## Концепція

### `if`, `else if`, `else`

```js
if (statusCode >= 500) {
  console.log('Серверна помилка');
} else if (statusCode >= 400) {
  console.log('Клієнтська помилка');
} else {
  console.log('Все гаразд');
}
```

Умови перевіряються **згори вниз**, виконується перша гілка з truthy-умовою, решта пропускаються.
Тому порядок має значення: якби перевірка `>= 400` стояла першою, статус `503` потрапив би в
«клієнтські».

Фігурні дужки ставимо завжди, навіть для одного рядка. Без них легко додати другий рядок, який
виконуватиметься вже без умови.

### Тернарний оператор

Коротка форма «якщо — то — інакше», яка **повертає значення** (ternary operator):

```js
const label = isPassed ? 'PASSED' : 'FAILED';
```

Добре для простого вибору з двох варіантів. Вкладені тернарні оператори
(`a ? b : c ? d : e`) читаються погано — у такому разі краще `if` або об'єкт-довідник.

### `switch`

Порівнює одне значення з багатьма варіантами через **строге** порівняння `===`:

```js
switch (browser) {
  case 'chromium':
  case 'chrome':          // кілька case на одну гілку — навмисне провалювання
    engine = 'Blink';
    break;
  case 'firefox':
    engine = 'Gecko';
    break;
  default:
    engine = 'unknown';
}
```

Найголовніше про `switch` — **провалювання** (fallthrough). Без `break` виконання продовжується в
наступний `case`, незалежно від його умови:

```js
switch (status) {
  case 'passed':
    color = 'green';      // забули break…
  case 'failed':
    color = 'red';        // …і пройдені тести стали червоними
    break;
}
```

Оскільки `switch` порівнює через `===`, `case 200:` не спрацює для рядка `'200'`.

### Ранній вихід (guard clause)

Замість глибокої вкладеності — спершу відсікаємо невалідні випадки і виходимо з функції через `return`:

```js
// Вкладено — важко читати
function getDiscountNested(user) {
  if (user !== null) {
    if (user.isActive) {
      if (user.orders > 10) {
        return 15;
      }
    }
  }
  return 0;
}

// Ранній вихід — кожна умова на своєму рядку
function getDiscount(user) {
  if (user === null) return 0;
  if (!user.isActive) return 0;
  if (user.orders <= 10) return 0;
  return 15;
}
```

Ранній вихід (guard clause) — дуже поширений прийом у тестовому коді: «немає даних — нема чого перевіряти».

### Об'єкт-довідник замість ланцюжка `if`

Коли умова — це просто відповідність «ключ → значення», ланцюжок `if` або `switch` замінює об'єкт:

```js
const BASE_URLS = {
  dev: 'https://dev.shop.test',
  staging: 'https://staging.shop.test',
  prod: 'https://shop.test',
};

const baseUrl = BASE_URLS[env] ?? BASE_URLS.dev;
```

Дані відокремлені від логіки: додати нове середовище — це один рядок, а не нова гілка. Квадратні
дужки `obj[key]` читають властивість, ім'я якої лежить у змінній; детально об'єкти розберемо в уроці 09.

### Межі діапазонів

Діапазон «від 200 до 299 включно» записують так:

```js
if (code >= 200 && code <= 299) { /* ... */ }
// або, для цілих чисел, з напіввідкритою межею:
if (code >= 200 && code < 300) { /* ... */ }
```

Обидва варіанти правильні. Помилка — змішати їх (`> 200 && <= 300`). Перевіряй кожну межу так, як
у тест-дизайні: значення **на** межі, **перед** нею і **після** неї (199, 200, 201 і 299, 300, 301).

<Aside type="tip" title="Що з цього для автотестів">
Перш ніж порівнювати, переконайся, що значення має очікуваний тип. Статус `'200'` (рядок) і `200`
(число) — це різні відповіді API, і `'200' >= 200` дорівнює `true` через неявне перетворення.
Перевірка типу на початку функції — це ранній вихід, який ловить порушення контракту.
</Aside>

## Типові помилки

1. **`>` замість `>=` на межі діапазону** — класичний «баг на одиницю». Перевіряй обидві межі тестом.
2. **Забутий `break` у `switch`** — виконання провалюється в наступний `case`.
3. **Неправильний порядок `else if`** — ширша умова, поставлена першою, «з'їдає» вужчі.
4. **`if (value)` замість явної перевірки** — `0`, `''` і `false` підуть у гілку «немає значення».
5. **`=` замість `===` в умові** — `if (status = 'failed')` присвоює і завжди дає truthy.
6. **Вкладені тернарні оператори** — працюють, але через місяць їх не прочитає ніхто, включно з автором.

## Самоперевірка

Відповідай уголос, потім розгорни відповідь.

<details>
<summary>Що станеться, якщо в `switch` забути `break`?</summary>

Виконання «провалиться» в наступний `case` і виконає його код, навіть якщо значення з ним не
збігається. Іноді це роблять навмисно — коли кілька `case` мають спільну гілку.
</details>

<details>
<summary>Яким порівнянням користується `switch`: `==` чи `===`?</summary>

Строгим `===`. Тому `case 200:` не спрацює для рядка `'200'`.
</details>

<details>
<summary>Що таке guard clause і чому його люблять?</summary>

Ранній вихід із функції (`return`) для невалідних або особливих випадків на самому початку. Він
прибирає вкладеність: основна логіка лишається на верхньому рівні й читається згори вниз.
</details>

<details>
<summary>Які значення ти перевіриш для умови «статус від 200 до 299 включно»?</summary>

Межі та сусідні значення: 199, 200, 201, 298, 299, 300. А ще — невалідні вхідні дані: рядок `'200'`,
дробове `200.5`, `null`.
</details>

<details>
<summary>Коли краще об'єкт-довідник, ніж `switch`?</summary>

Коли кожна гілка лише повертає значення для свого ключа. Дані відокремлюються від логіки, і новий
варіант — це один рядок в об'єкті.
</details>
